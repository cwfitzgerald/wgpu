#### #10506: Reduce Metal command-buffer memory for multi-pass encoders (@matthargett)
- **Verdict:** Needs a bit of work
- **Waiting on:** maintainer (no reviews yet; inner-daemons is requested). The maintainer must approve the design first: the PR adds a new `wgpu_hal::Capabilities::pass_barriers_are_noop` and changes the core pass-encoding structure in wgpu-core, which Firefox uses.
- **CI:** incomplete. Most Mac jobs were cancelled at about 19:25 UTC on 2026-11-05 (API Validation/Operation Mac, Other Mac, Clippy MacOS/IOS/VisionOS aarch64, Core MSRV MacOS). The same timestamp shows on #9679, which suggests a runner-wide cancellation, not a PR failure. "Test Mac aarch64" passed. All other jobs are green. A rerun is necessary.
- **Summary:** When the backend says that barriers and query resets are no-ops (Metal, Noop), and a conservative preflight finds no discarded-texture fixups, no indirect validation and no bundles, render and compute passes append to the current native command buffer. Without this, each pass gets its own command buffer plus a pre-pass buffer. The PR reports that this cuts about 2.3 MiB of driver memory per pass (a 97% footprint reduction in the 800-pass repro) and removes the 4096-pass limit.
- **Findings:**
  1. [high] `wgpu-core/src/command/render.rs:2305` and `:2803` In append mode, `transit.encode_deferred_multi_draws()` runs after the pass in the same MTLCommandBuffer. This breaks the HAL contract from #9640, which is already in trunk: the deferred work must go in a command buffer that executes *before* the pass. The preflight splits `DrawIndirect` and `MultiDrawIndirectCount` only when `device.indirect_validation.is_some()`. With `InstanceFlags::VALIDATION_INDIRECT_CALL` cleared, a `multi_draw_indirect` of 512 or more draws (the trunk ICB path) runs an ICB that has not been generated yet (stale commands from the pool, or garbage). That is wrong rendering, and possibly a GPU fault through a safe API. #9679 adds more deferred work (the ICB count range and clamped args), which makes this worse. Fix: always split on `DrawIndirect { count > 1 }` and `MultiDrawIndirectCount`, or ask the HAL whether deferred multi-draws are pending. Add a test that clears `VALIDATION_INDIRECT_CALL`.
  2. [medium] `wgpu-core/src/command/render.rs:2754`, `wgpu-core/src/command/compute.rs:907` `assert!(!append || pending_discard_init_fixups.is_empty())` panics in wgpu-core if the preflight and the real init tracking ever disagree, and both depend on untrusted input. I could not find such a mismatch: attachment Load/D3 handling, read-only depth, bind groups and bundles all match. But the invariant depends on two separate code paths staying in sync. A non-panicking fallback is safer, for example recording the fixups into a new buffer and swapping, or at minimum a `debug_assert` plus a forced split.
  3. [medium] The design adds a new HAL-wide capability, and it weakens the `transition_buffers` contract in `wgpu-hal/src/lib.rs`. The alternative is a Metal-local solution, for example reusing one MTLCommandBuffer across `begin_encoding`/`end_encoding` inside the Metal HAL. That would not touch wgpu-core's pass structure. The maintainer should decide which approach is acceptable before reviewing details.
  4. [low] `CHANGELOG.md` The entry says that passes with indirect draws split only "with indirect validation enabled". This documents the bug in finding 1.
  5. [low] The description has a truncated sentence ("I have some adjustments in"). The full-suite run reports 2 failures that the author calls unrelated (`subgroup_operations` unexpectedly passing, `written_timestamp_resolves_to_nonzero`). They should be confirmed against a clean trunk run on the same machine.
- **To land:** always split for multi-draw indirect and count draws (or query the HAL for pending deferred work) and add a test with indirect validation off. Replace the asserts with a safe fallback. Get maintainer sign-off on the HAL-capability approach. Rerun the cancelled Mac CI.
- **Depth:** targeted. I read the wgpu-core preflight, the transit/append logic and the HAL capability in full. I skimmed the tests. I did not check every query-resolve or TLAS path for ordering assumptions.

#### #9679: Use Metal ICBs for multi-draw indirect count (@matthargett)
- **Verdict:** Needs a bit of work

- **CI:** incomplete. Mac jobs were cancelled in the same runner-wide event as #10506 (Test Mac aarch64, API Validation Mac, Other Mac, Clippy MacOS/IOS, MSRV MacOS). API Operation Mac passed. All other jobs are green. A rerun is necessary.
- **Summary:** Exposes `MULTI_DRAW_INDIRECT_COUNT` on Metal. Count draws run through a GPU-generated ICB, with a GPU-clamped execution range. Pipelines that cannot run in an ICB fall back to a GPU-clamped, zero-padded copy of the arguments plus a CPU loop of `max_count` indirect draws. The PR also adds `wgt::INDIRECT_BUFFER_OFFSET_ALIGNMENT` and count-buffer offset validation (a real validation fix on all backends), and the deno `chromium-experimental-multi-draw-indirect` surface.
- **Findings:**
  1. [high, interaction] This PR conflicts with #10506 (same author). There is no large textual conflict: both edit `wgpu-core/src/command/render.rs`, but in different regions (#10506 in `encode_render_pass`, #9679 in the error enum and `multi_draw_indirect_count`), and both add to the CHANGELOG Metal section. The conflict is semantic. #9679's count path depends on `encode_deferred_multi_draws` running in the pre-pass buffer. #10506 appends count draws to the pass's buffer when indirect validation is off, so the ICB execution range and the clamped args would be produced after the pass that consumes them. Neither PR depends on the other (both are based on 545f277, and #9640 is already in trunk). Whichever lands second must handle this, and the best place to fix it is in #10506 (see its finding 1).
  2. [medium] `wgpu-core/src/command/render.rs:3399` wgpu-core indirect validation does not cover count draws. This is an existing gap on DX12 and Vulkan, which have robust buffer access. Metal does not guarantee bounds-checked vertex or index fetch, which is why indirect validation exists. This PR exposes unvalidated GPU-provided `first_vertex`, `base_vertex`, `first_index` and instance values on Metal through the safe `wgpu` API. Either extend indirect validation to count draws, or document the risk and get maintainer sign-off.
  3. [medium] `wgpu-hal/src/metal/icb.rs:999` and `wgpu-hal/src/metal/command.rs:1746/1804/1871` The fallback allocates a new private buffer of `max_count * stride` bytes on every count-draw call (not pooled), then issues `max_count` CPU-side indirect draws, most of which are zeroed. A large `max_count` on a textured-fragment pipeline, which the PR says is common on current Apple drivers, gives a large per-frame allocation and a CPU cost of O(max_count). This is a performance cliff, not a safety problem. Pool the buffer, or document the cost.
  4. [low] `wgpu-types/src/features.rs:573` The existing doc says the feature "implies that all calls to multi_draw_indirect ... are not being emulated with a series of draw_indirect calls". On Metal this is false (fixed-count draws below 512, and the fallback path). The new Metal note contradicts the sentence above it. Reword it.
  5. [low] `wgpu-hal/src/metal/adapter.rs:138` If the ICB kernels fail to compile, device creation fails with `DeviceError::Unexpected` when the feature was requested. It would be cleaner to not advertise the feature in that case. Separately, the 92-commit history needs a squash (the author already plans one).
- **To land:** split the deno changes into their own PR (the maintainer asked for this; also fix the missing feature check on `multiDrawIndirect` without a count buffer). Decide how to handle count-draw argument validation on Metal. Fix the feature doc wording. Rerun Mac CI. Coordinate with #10506 on deferred multi-draw ordering.
- **Depth:** targeted. I read the wgpu-core, wgpu-types, adapter, Metal shader and `command.rs` count paths, and the `icb.rs` count/fallback functions. I did not review the rest of the `icb.rs` rewrite (480+/146-, including pooling and lifetime), the 401-line test file or the deno code in detail.
