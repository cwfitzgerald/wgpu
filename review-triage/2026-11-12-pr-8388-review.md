>   > **A failed submit can deadlock the interop queue and the CPU** (`dxgi.rs:1142`, `wgpu-hal/src/vulkan/mod.rs:1581`)
>   > 
>   > `get_submit_signal_semaphore` takes a new `vulkan_progress` value and writes it to `sync.vulkan_progress_value` before `relay_semaphores.advance()` and `vkQueueSubmit` run. Either of those can fail.
>   > - If one fails, `present` issues `ID3D12CommandQueue::Wait` for a value that will never be signalled.

>   > - Vulkan device loss leads to the same hang.
>   > 
>   > Suggested fixes:
>   > - Only commit the value once the submit succeeds, or roll it back on error.
>   > - Use a real event with `WaitForSingleObject` and a timeout in `wait_for_value`, so this fails with `Lost` instead of hanging.
>   >

### B5

Failed submit deadlock: `get_submit_signal_semaphore` writes the new `vulkan_progress` value before `relay_semaphores.advance()` and `vkQueueSubmit`; on failure `present` makes the interop queue wait for a value that is never signalled.

Notes: Status: covered by `ynrpmkxu` "fixup: keep the DXGI interop fence from hanging after failures"; the submit path is not changed (D3). wgpu-core loses the device on any failed submit, so nothing continues from that state. The present after a failed submit waits at most 1 s and returns `DeviceError::Lost`; teardown signals the missing values from the CPU. See E1 and E2.

### B6

After that, every `wait_for_value` blocks forever, including in `release_resources`, because `SetEventOnCompletion` with a null event waits without limit. Vulkan device loss gives the same hang.

Notes: Status: fixed in `ynrpmkxu` "fixup: keep the DXGI interop fence from hanging after failures". See E3. `ynrpmkxu` (E4) fixes a different way to reach the same hang.

### B7

Suggested fix 1: commit the value only when the submit succeeds, or roll it back on error.

Notes: Status: not done as suggested, by decision (D3). `Queue::submit` is identical to trunk, and the DXGI guard commits the value when the guard is taken ([dxgi.rs:1271](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1271), called from [mod.rs:1599](wgpu-hal/src/vulkan/mod.rs:1599)), as in the original PR. Reason: wgpu-core loses the device on any failed submit, so a rollback protects state that nothing uses again. The teardown signal and the timeout (B6, B8) remove the hang.

### B8

Suggested fix 2: use a real event with `WaitForSingleObject` and a timeout in `wait_for_value`, so the failure is `Lost` and not a hang.

Notes: Status: fixed in `ynrpmkxu`. Timeout 1 s (equal to the wgpu-core acquire timeout), in all three callers: acquire, present and teardown. See E3 and D12.

Before: each acquire waited on the waitable object, which consumes one frame. A discarded texture is never presented, so nothing gave the frame back; after about `maximum_frame_latency` discards in a row every acquire could time out. Now a `waited_for_frame` flag skips the wait until a successful present gives the frame back: Vulkan [dxgi.rs:1077](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1077), [dxgi.rs:1200](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1200); DX12 [dx12/mod.rs:1380](wgpu-hal/src/dx12/mod.rs:1380), [dx12/mod.rs:1484](wgpu-hal/src/dx12/mod.rs:1484). `discard_texture` itself is still a no-op ([dxgi.rs:1150](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1150)); related: #5723.

### E15. Occluded, minimized, and zero-size windows

Status: decided, no change.

wgpu-core rejects a zero-area configuration before the HAL is called. A minimized window reports a 0x0 `current_extent`. Occlusion is a success code from `Present` (E13). `acquire` never reports `suboptimal` or `Outdated`; on a resize without reconfigure, DXGI scales (`DXGI_SCALING_STRETCH`). No error-handling issue found.

### E16. Configure or present with a stale acquired texture

Status: decided, no change.

wgpu-core destroys the acquired texture in `unconfigure_inner` before reconfiguring, so a texture from an old swapchain cannot be presented through wgpu-core. A direct wgpu-hal user could present one: `self.buffers[index]` ([dxgi.rs:1165](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1165)) then panics if the new swapchain has fewer buffers, or uses the wrong sync state. That is outside the HAL contract, and the native swapchain has the same exposure.

### E17. Unconfigure or drop with GPU work in flight

Status: fixed in `zoxlwzoq` "fixup: assert DXGI swapchain release, count back buffers".

`release_resources` ([dxgi.rs:1045](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1045)) runs `device_wait_idle` (error ignored), signals unsubmitted `vulkan_progress` values, and then waits for the last `interop_progress` value. It returns after at most the 1 s timeout, ignores a wait error, and then destroys the buffers (D2). `DxgiSwapchain` now has a `Drop` with `debug_assert!(self.buffers.is_empty())` ([dxgi.rs:1001](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1001)). wgpu-core always calls `unconfigure` (also from `Surface::drop`), so a drop without `release_resources` is only reachable through direct wgpu-hal use.

### E18. Texture counters for the back buffers

Status: fixed in `zoxlwzoq` "fixup: assert DXGI swapchain release, count back buffers".

`destroy_texture` subtracts from `counters.textures`, but the import (`texture_from_raw`) never added. Now `add_raw_texture` is called after each import ([dxgi.rs:781](wgpu-hal/src/vulkan/swapchain/dxgi.rs:781)).

### E21. Acquire partial failure

Status: decided, no change.

If `execute_sync_command_list` fails before `ExecuteCommandLists` (allocator or list `Reset`, `Close`), nothing is submitted; the next acquire resets again. If `Signal` fails after the list was submitted, `acquire_submit` keeps the older value, so the next reuse of that allocator could reset it while the list runs; but `Signal` fails only on device removal or OOM, where D3D12 reports fences complete or the device is lost anyway. Acquire is at [dxgi.rs:1072](wgpu-hal/src/vulkan/swapchain/dxgi.rs:1072).

## Q. Queue family ownership transfer

Status: fixed in `lxkvvmlv` "fixup: release DXGI back buffers to the external queue family on present", on top of `ynrpmkxu`. Runtime at the tip: `cube` and the `wgpu_surface` test run with both DXGI kinds on an NVIDIA RTX 4070 (see the header). Not tested on AMD or Intel.

Review body bullet: "Possibly a queue transfer is needed for these surfaces in addition to the `present_layout` adjustment?" (bug 2074667, which is about the Firefox Linux DMA-BUF path).

What the commit does:

- `vulkan::Texture::present_layout` is replaced by `present_transition: PresentTransition` (`PresentSrc` or `ReleaseToExternal`, [mod.rs:985](wgpu-hal/src/vulkan/mod.rs:985)). DXGI back buffers are `ReleaseToExternal`; all other textures are `PresentSrc` and behave as before.
- In `transition_textures`, a `ReleaseToExternal` texture gets:
  - transition to `PRESENT`: release, `src = device family`, `dst = VK_QUEUE_FAMILY_EXTERNAL`, `newLayout = GENERAL`.
  - transition from `PRESENT` (a later submit in the same frame): acquire, `src = VK_QUEUE_FAMILY_EXTERNAL`, `dst = device family`, `oldLayout = GENERAL`.
  - `UNINITIALIZED -> X` at frame start stays an implicit acquire (contents are not needed).
- A transfer set by the caller on `TextureBarrier::queue_family_ownership_transfer` takes precedence; a `debug_assert!` fires if both apply.

Naming: decided and done (D8).

Unverified:

- The effect on AMD and Intel (compression metadata) is not checked; NVIDIA is expected to show no difference.
- Validation layers do not check VUID-12331/12332 for `D3D12_RESOURCE` handles, so they will not confirm the barriers. Validation layers are not installed on this machine.
- The mid-frame acquire follows a release to `EXTERNAL` that no external API used in between (Dawn does the same on end/begin access). The relay semaphore that orders the two submits waits at `TOP_OF_PIPE`, while the spec notes that only `ALL_COMMANDS` formally waits for transfer operations. Both are pre-existing patterns; not changed.

Draft reply (not posted; the short version to send is in `2026-11-13-pr-8388-replies.md`):

> Thanks, good catch. The spec requires an explicit ownership transfer for external-memory resources when contents must stay valid; implicit ownership leaves them undefined (External Resource Sharing; Queue Family Ownership Transfer).
>
> - Acquire (D3D12 -> Vulkan): wgpu-core starts each acquired surface texture as `UNINITIALIZED`, so the first barrier is `UNDEFINED -> X`. That is a valid implicit acquire, and the spec says to skip the transfer when contents are not needed. ANGLE does the same.
> - Present (Vulkan -> D3D12/DXGI): the barrier to `PRESENT` is now a release with `dstQueueFamilyIndex = VK_QUEUE_FAMILY_EXTERNAL` and `newLayout = GENERAL`. If a later submit in the same frame uses the texture again, the barrier out of `PRESENT` is the matching acquire from `VK_QUEUE_FAMILY_EXTERNAL` with `oldLayout = GENERAL`. This follows the rules Khronos wrote for D3D11 handles (VUID-VkImageMemoryBarrier-dstQueueFamilyIndex-12331 / srcQueueFamilyIndex-12332) and what Dawn and Chromium do.
> - I used `EXTERNAL` and not `FOREIGN` (the Firefox bug is about Linux DMA-BUF), because the D3D12 device is on the same LUID-matched adapter and driver, and `FOREIGN` needs `VK_EXT_queue_family_foreign`.
>
> Native swapchain textures and imported textures are unchanged.
